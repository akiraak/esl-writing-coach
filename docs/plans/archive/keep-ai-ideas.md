# AI案が画面を切り替えると消える

> 2026-11-11: **案 F（全てを SQLite に入れる）に決め、`sqlite-storage.md` で実装した**。以下は検討の記録。

## 目的・背景

右ペインの「AI案」（テーマの候補・理由と例の候補・アウトラインの指摘）の結果が、画面を切り替えると消えてしまう。
AI の呼び出しは時間（10 秒前後）も API の料金もかかるので、見たい結果を取り直すのは避けたい。

## 調査結果（2026-11-11）

### 消えるとき・消えないとき

| 操作 | AI案 |
|---|---|
| 同じパラグラフの中で段階（STEP 1〜3）を移る | 残る |
| 右ペインのタブを「構成」などに替えて戻る | 残る |
| ヘッダから学習ガイド・振り返り・一覧へ移って戻る | **消える** |
| 別のパラグラフを開いて戻る | **消える** |
| ページを再読み込みする | **消える** |
| 呼び出し中に上のどれかで画面を離れる | **結果が捨てられる**（API の呼び出しは終わるまで続き、料金はかかる） |

### 原因

1. **結果を DOM の中にしか持っていない**。`src/browser/ideas-pane.ts` の `createIdeasPanel()` は、候補のデータを変数に持たず、
   描いた要素（`themesList`・`ideasList`・`reviewResult`）だけが結果になっている。分野・キーワードの入力欄も同じ
2. **パネルは編集画面ごとに作り直される**。`src/browser/views/edit.ts:106` の `renderEdit()` の中で作り、
   `src/browser/main.ts:52` は編集画面以外へ移ると `current` を捨てるので、戻ると `renderEdit()` が空のパネルを新しく作る
   （段階の切り替えは `navigate()` で同じ画面を使い回すので残る。タブの切り替えも `guide-content.ts:162` が同じ要素を返すので残る）
3. **これは仕様どおり**。`docs/plans/archive/ai-ideas.md` で「保存しない: 候補は画面の中だけ（編集画面を開いている間）」と決め、
   アウトラインの指摘も同じにした（`ideas-pane.ts:19` の注釈にもある）。ただ、ヘッダの「学習ガイド」へ移るなど、
   ふだんの使い方でも「編集画面を開いている間」が切れることを考えていなかった

比べると「採点」は `feedback.json` に保存し、開くたびに `readFeedback()` で読むので消えない。

## 改善案

### 案 A: ブラウザのメモリにパラグラフごとに持つ（推奨）

- モジュールの変数 `Map<パラグラフの id, AI案の状態>` に、データ（テーマの候補・理由と例の候補・指摘・分野の入力・エラー）と
  **呼び出し中の Promise** を持つ。パネルを作るときにそこから描き直す
- 呼び出し中に画面を離れても、終わった結果は Map に入るので、戻れば見える（「考えています…」の途中なら続きから）
- 出したときのテーマ・アウトラインも持ち、今と違えば「テーマを変えたあとの候補です」「アウトラインを直したあとです」と知らせる
  （採点の「本文が変わっています」と同じ考え方）
- 消えるのは再読み込み・タブを閉じたときだけ。「保存しない」の決めごとはそのまま
- 変更は `ideas-pane.ts`（状態を外に出す）と `edit.ts`（id を渡す）だけ。サーバ・Dropbox は変わらない

### 案 B: 案 A + `sessionStorage`

- 案 A に加えて、同じ状態を `sessionStorage` にも書く。再読み込みしても残る（タブを閉じると消える）
- 手間は少し増えるだけ。再読み込みをよくするなら足す価値がある

### 案 C: Dropbox に保存する（`ideas.json`）

- 採点の `feedback.json` と同じく、パラグラフのフォルダに最新の 1 回分を書く。別の PC・後日に開いても残る
- 「結果は保存しない」の仕様を変えることになる。サーバの API（読み書き・rev）とテストが増える
- テーマの候補はパラグラフを作る前の段階で使うものなので、パラグラフに保存する意味は薄い。保存するなら理由・例の候補と指摘だけ

Dropbox はファイル 1 つの読み込みに時間がかかるため、開くたびに待たされる（2026-11-11 ユーザー指摘）。そこで DB の案 D・E を足した。

### 案 D: サーバの SQLite に保存する（`node:sqlite`）

- Node 22 に入っている `node:sqlite`（`DatabaseSync`）を使う。**依存は増えない**（この PC の Node 22.22 で動くことを確かめた。
  起動時に `ExperimentalWarning` が 1 行出るので、`--disable-warning=ExperimentalWarning` で消す）
- DB のファイルはリポジトリの `data/esl-writing.db`（`.gitignore` に足す）。**Dropbox のフォルダには置かない**（同期中に書くと壊れることがあるため）
- テーブルは 1 つ: `ai_results(paragraph_id, kind, input_json, result_json, created_at)`。主キーは `(paragraph_id, kind)`。
  `kind` は `themes`・`ideas`・`outline_review`。種類ごとに最新の 1 回分を上書きする（採点と同じ「最新だけ」）。`input_json` には出したときのテーマ・条件・アウトライン・分野を入れ、今と違えば知らせる
- **AI の呼び出しが終わったらサーバが DB に書く**ので、呼び出し中にブラウザが画面を離れても結果は残る
- API: `GET /api/paragraphs/:id/ai` で 3 種類をまとめて返す。今の `POST /api/ai/themes` などに `paragraphId` を足し、終わったら書く
- パラグラフを削除したら、同じ id の行も消す（`DELETE /api/paragraphs/:id` の中で）
- 読み込みはミリ秒単位。テストは `:memory:` の DB で `node --test` から確かめられる
- 弱いところ: DB はこの PC にしか無い（別の PC で開くと出ない。バックアップも Dropbox に入らない）。
  ただ、このアプリは「自分の PC でだけ動かす」と決めていて、AI案は取り直せるものなので、失っても困らない

### 案 E: ブラウザの IndexedDB に保存する

- サーバは変えない。ブラウザの DB に、パラグラフの id ごとに持つ。再起動しても残る
- 弱いところ:
  - **開いた名前ごとに別の入れ物になる**（`esl-writing.localhost:3016` と `127.0.0.1:3016` では見える結果が違う）
  - ブラウザのサイトデータを消すと消える。パラグラフを削除しても残る（掃除が要る）
  - 呼び出し中に画面を離れたときは、ブラウザ側で受け取ってから書くことになり、タブを閉じると失われる
  - テストは DOM 抜きで回しにくい（IndexedDB は Node に無い）

### 案 F: 全てを DB（サーバの SQLite）に入れる

2026-11-11 ユーザー要望で検討。AI案だけでなく、課題・アウトライン・下書き・採点も SQLite に置き、Dropbox はやめる（またはバックアップだけにする）。

#### 今の遅さ（2026-11-11 に今のサーバで測った）

| API | 時間 |
|---|---|
| 一覧 `GET /api/paragraphs` | 0.50〜0.60 秒 |
| 段階 1 つ `GET .../stages/:stage` | 0.47〜0.78 秒（編集画面は 3 つを並べて読むので約 0.8 秒） |
| 採点 `GET .../feedback` | 0.46 秒 |
| 振り返り `GET /api/review` | 0.43 秒（覚えてある分。初回はもっとかかる） |

保存も 1 回ごとに同じくらいかかるが、自動保存は裏で行うので待たされるのは主に**開くとき**。SQLite なら全部ミリ秒単位になる。

#### 作り

- 表: `paragraphs(id, created_on, updated_at)`、`stages(paragraph_id, stage, text, version, updated_at)`、
  `feedbacks(paragraph_id, json, version)`、`ai_results`（案 D と同じ）
- **保存の競合の判定は残す**: `rev` の代わりに `version`（保存のたびに 1 増やす）。`UPDATE ... WHERE version = ?` で 0 行なら 409。
  タブを 2 つ開いて同じパラグラフを書いたときの上書きを防ぐ（今の自動保存・競合の画面はそのまま使える）
- `src/paragraphs/store.ts` の `ParagraphStore`（一覧・段階の読み書き・作成・削除・採点）は保存先を隠した形になっているので、
  **同じ形の SQLite 版を作って差し替える**。API とブラウザはほとんど変わらない（`rev` に version の文字列が入るだけ）
- 要らなくなるもの: Dropbox のクライアント（トークンの更新・`list_folder/continue`）、一覧のテーマと振り返りの読み置き（`themes.ts`・`feedbacks.ts`。SQL で直接取れる）、
  改行コード・BOM を戻す処理（`text.ts`。ほかのアプリで開かなくなるため）、`dropbox:check`・`dropbox:smoke`
- 削除は今は「Dropbox の削除済みから戻せる」。DB では行を消すと戻せないので、`deleted_at` を付ける（一覧に出さないだけ）にするか決める
- 今 Dropbox にあるパラグラフは、1 回だけ読み込むスクリプトで DB に移す

#### 失うもの

1. **バックアップ**: Dropbox は別の場所に置かれ、ファイルの版も 30 日戻せる。DB のファイルはこの PC だけにあるので、PC が壊れると消える
   → **毎日（起動時など）DB のコピーを Dropbox に上げる**（`VACUUM INTO` で 1 ファイルにして上げる。同期ではなくバックアップだけ。戻すときは手で置き換える）
2. **別の PC で使うこと**: 今もサーバは 1 台の PC で動かす前提なので影響は小さい。2 台で使い分けるならこの案は合わない
3. **ほかのアプリで開くこと**: `outline.txt` を daily-note のマップで開く・ファイルを手で直す、ができなくなる。必要なら書き出しで代わりにする
4. **決めたことを変える**: 2026-11-08 の「Dropbox 上のファイルとして保存する（daily-note と同じ）」をやめることになる。CLAUDE.md の「データ保存」の節を書き直す

#### 手間

案 D よりずっと大きい。保存層の作り直し・移し替えのスクリプト・バックアップ・テストの書き直し（`paragraph-store.test.ts`・`themes.test.ts` など）・CLAUDE.md の書き直し。
Phase に分けるなら: (1) SQLite の保存層（`ParagraphStore` の SQLite 版とテスト）→ (2) 差し替えと AI案の保存 → (3) Dropbox からの移し替え → (4) Dropbox へのバックアップ → (5) Dropbox の部分の削除と CLAUDE.md。
選ぶなら別のプラン（`docs/plans/sqlite-storage.md`）に分ける。

### 案 G: Dropbox のままで、読み込みをサーバで覚えておく（参考）

- 全てを Dropbox に置いたまま、サーバが読んだ中身をメモリ（か SQLite）に覚えておき、2 回目からはそこから返す
- ほかで書き換えられたかは `list_folder/longpoll` で裏で見張って、変わったファイルだけ忘れる
- Dropbox の良いところ（バックアップ・別の PC・daily-note のマップ）は残るが、サーバを起動して最初に開くときは遅いまま。見張りの分だけ作りが込み入る

### 推奨

（AI案だけを直すなら）**案 D（サーバの SQLite）+ 案 A（呼び出し中の分だけブラウザのメモリで持つ）**。
遅さそのものを直したいなら **案 F（全てを SQLite + 毎日 Dropbox へバックアップ）**。決める前に確かめたいこと:
別の PC でも使うか、`outline.txt` を daily-note のマップで開くことがあるか。どちらも「無い」なら案 F が一番すっきりする。

以下は案 D + A を選んだときの話。

- 速さは Dropbox より大きく上がり、IndexedDB と同じくらい。開いた名前・ブラウザに左右されず、パラグラフの削除とも揃えられる
- データをサーバが持つという今の作りに合い、テストもほかの保存層と同じ形で書ける
- 案 A は、呼び出し中に戻ったときに「考えています…」を続けて出すためだけに使う（結果そのものは DB から読む）
- パラグラフの本文などは今までどおり Dropbox に置く。DB に置くのは「失ってもかまわない AI案」だけにして、データの置き場が 2 つになることの影響を小さくする
- 別の PC でも見たいなら案 C だが、読み込みの遅さは残る

## 影響範囲（案 D + A の場合）

- 新規 `src/db/`（DB を開く・テーブルを作る・AI案の読み書き）。`src/config.ts` に DB のパス（`ESL_DB_PATH`、既定は `data/esl-writing.db`）
- `src/server/api.ts`: `GET /api/paragraphs/:id/ai` を足し、AI案の 3 つの API で結果を書く。削除で行を消す
- `src/browser/ideas-pane.ts`: 開いたら DB の結果を読んで描く。出したときの入力と今が違えば知らせる。呼び出し中の Promise はパラグラフごとにメモリに持つ
- `src/browser/views/edit.ts`: `createIdeasPanel()` に id を渡す
- `run-server.sh`・`package.json` の `start`: `--disable-warning=ExperimentalWarning`。`.gitignore` に `data/`
- CLAUDE.md: 「データ保存」に「AI案だけはローカルの SQLite」を、「AI のアイデア出し」の「結果は保存しない」を書き換える

## テスト方針

- DB の読み書き（上書き・パラグラフの削除で消える・壊れた JSON は無いものとして扱う）を `:memory:` で確かめる
- API: 呼び出しが終わったら書くこと、`GET` で 3 種類が返ること（AI は今と同じく偽の呼び出し）
- 出したときの入力と今の比較は純関数にしてテストする
- ブラウザで: 候補を出す → 学習ガイドへ移る → 戻る／再読み込み／サーバを再起動、で残ること。呼び出し中に移って戻ると結果が出ること。
  別のパラグラフには出ないこと。テーマを変えると知らせが出ること。削除で消えること
