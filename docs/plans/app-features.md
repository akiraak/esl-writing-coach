# アプリの機能を決める

## 目的・背景

2026-11-07 にプロジェクトをゼロから作り直すことにし、コンセプトを「ESL の授業で書くパラグラフを、学びながら書くためのツール（自分専用・PC 専用）」と決めた。機能と画面構成はまだ何も決まっていない。実装と技術選定の前提になるので、先に機能を決めて文書にまとめる。

旧実装は「記事を書くと AI が添削とアドバイスを返す」汎用の英作文添削ツールだった。新しいコンセプトでは「パラグラフの書き方を**学ぶ**」ことに重心を置くため、旧機能はそのままでは引き継がず、必要なものだけ選び直す。

## 対応方針

ユーザーへのヒアリングで要件を集め、Claude が機能案にまとめ、ユーザーが確定する、という流れで進める。コードは書かない。

### Phase 1: ヒアリング

次の観点で、授業の実態と、ツールに期待することを確認する。

- **授業と課題**
  - 課題として書くパラグラフの種類（opinion / compare & contrast / process / cause & effect / narrative など）
  - 課題で与えられるもの（お題・ルーブリック・語数制限・締切・配布プリント）
  - 提出方法（Word / Google Docs / 手書き / LMS）と、ツールから持ち出す形式
  - 授業で教わる構成の型（topic sentence / supporting sentences / concluding sentence、transition words など）
- **学び方**
  - 「学ぶ」部分で欲しいもの（構成のガイド、パートごとのフィードバック、例文、チェックリスト、語彙・表現集など）
  - 書く流れ（アイデア出し → アウトライン → 下書き → 推敲、のどこを支援するか）
  - 日本語での下書きやメモを許すか
- **AI の関わり方**
  - AI に任せる範囲（構成への指摘・文法の添削・書き直し案の提示）
  - 課題として自力で書く必要がある前提で、AI がどこまで書き直してよいか（ヒントに留めるか、添削済み全文を出すか）
- **データ**（保存方式は daily-note と同じく Dropbox 上のファイルに決定済み。2026-11-08。詳細は `CLAUDE.md` の「データ保存」）
  - 課題やパラグラフを残すか、版の履歴を持つか
  - Dropbox 上の保存先フォルダ、ファイル形式（`.txt` / `.md` など）、ファイルの配置と命名
  - 課題文・下書き・AI のフィードバックを 1 ファイルにまとめるか、別ファイルに分けるか
  - daily-note と Dropbox アプリ（トークン）を共用するか、別に作るか
  - 旧 DB の記事（`/home/ubuntu/esl-writing-coach-backup-2026-11-07/` に退避済み）を Dropbox のファイルへ移行するか
  - 旧実装で構想していた「課題プリントの画像を取り込む（OCR）」機能を入れるか

### Phase 2: 機能案の作成

ヒアリング結果をもとに、Claude が機能一覧を作る。

- 各機能を **MVP（最初に作る）** と **後回し** に分ける
- 画面構成と画面遷移を簡単にまとめる（PC 専用のため、横幅を活かした複数ペインのレイアウトを前提にしてよい）
- 保存するデータの大まかな項目と、Dropbox 上のファイル配置を挙げる

### Phase 3: レビューと確定

- ユーザーが機能案を確認し、修正点を反映する
- 確定版を `CLAUDE.md` の「アプリの内容」に書く
- MVP の各機能を実装タスクとして `TODO.md` に追加する
- 次のタスク「技術スタックを決める」を `TODO.md` に追加する（技術選定はこのタスクの対象外）

## 影響範囲

- `CLAUDE.md`: 「アプリの内容」セクションを埋める
- `TODO.md`: 実装タスクと、技術スタック選定タスクを追加する
- コード: 変更なし

## テスト方針

コードを書かないタスクのため、自動テストはない。次の点を確認して完了とする。

- `CLAUDE.md` の「アプリの内容」だけを読めば、何を作るか（MVP の範囲・画面構成・データ）が分かる
- ヒアリングの各観点に、決定または「やらない」「後回し」の判断が付いている
- ユーザーが確定版を承認している
